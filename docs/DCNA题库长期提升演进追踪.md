# DCNA 题库长期提升演进追踪

> 文档状态：持续维护  
> 建立日期：2026-11-21  
> 最近更新：2026-11-21  
> 适用题库：`exams-dn42/dcna-dc-01.xml`  
> 当前定位：DN42 Certified Network Associate（DCNA）练习题库，并逐步发展为运营商网络工程师培养与筛选工具

## 1. 文档目的与维护约定

### 1.1 文档目的

本文档是 DCNA 题库长期演进的**设计与决策主文档**，用于持续记录：

1. 题库当前设计、覆盖范围和质量基线；
2. 已识别的不足、技术债和题目质量问题；
3. 改进目标、优先级、实施步骤和验收标准；
4. 每轮改进的实际进展、结果、偏差和后续决策；
5. 与 CCNA、CCNP Service Provider 能力体系及 DN42 特色之间的对应关系。

题库 XML 是实际题目内容的来源；本文档是“为什么这样设计、下一步改什么、已经改了什么”的来源。两者不得相互替代。

### 1.2 强制维护约定

**今后每当 DCNA 题库要新增、删除、重写、调整答案、改变配比或改变筛选规则时，都必须遵循以下流程：**

1. **改进前读取本文档**，至少检查当前基线、未完成任务、题目设计规范、进行中决策和历史变更记录。
2. **改进时参考本文档**，将工作关联到既定的路线图任务编号；新增方向必须先补充设计和理由，不能只用“Add question”代替设计记录。
3. **改进后回写本文档**，更新实际题量、领域分布、任务状态、验收结果和变更台账。
4. 计划没有实施时，不得标记为完成；只完成一部分时，记录实际完成数量及遗留事项。
5. 修改既有计划时，保留原决策和变更原因，不得通过覆盖历史来制造“始终如此”的假象。
6. 发现题目事实错误、歧义或答案争议时，除修正 XML 外，还应在质量问题和变更台账中记录。
7. 每次回写至少包括：日期、涉及题号、实际变更、验证方式、对基线指标的影响、后续行动。

### 1.3 状态定义

- **未开始**：尚未进入实际编写或修改。
- **进行中**：已有实际工作，但尚未达到验收标准。
- **待复核**：已有答案或设计，但需要第二人技术复核或实测。
- **已完成**：内容已落盘、通过约定验证，并更新基线。
- **暂缓**：有明确原因和重新评估条件，不等同于完成。
- **阻塞**：依赖 schema、平台能力、外部资料或决策，记录具体阻塞项。

## 2. 题库使命与设计原则

### 2.1 双重目标

DCNA 题库同时服务于：

- **培养**：帮助学习者建立从网络基础到运营商核心技术的系统知识，并通过场景题学习排查问题。
- **筛选**：识别候选人是否具备运营商网络工程师所需的基础推理、协议理解、读图读表和故障定位能力。

两种目标不能完全混用。练习题应提供反馈和解析；筛选题应控制重复曝光、按领域抽样，并提供领域小分。

### 2.2 能力定位

- 以 **CCNA 所代表的通用网络基础能力**作为入门基线。
- 以 **CCNP Service Provider 的 SPCOR 和 SPRI 所代表的运营商核心与高级路由能力**作为进阶参照。
- 保留 DN42 的注册表、IPAM、DNS、RPKI、隧道和实际运营场景，形成区别于通用厂商认证的实践特色。
- 对标能力而非复制厂商考试，不要求所有题目采用 Cisco CLI；可使用 Cisco IOS／IOS XR、BIRD、FRRouting、Linux 等，但题干必须明确平台和版本边界。

### 2.3 题型边界

当前以可自动评分的客观题为限：

- 单选题；
- 多选题；
- 拖拽匹配、排序和图像拖放题；
- 带拓扑、配置、CLI 输出、日志或抓包截图的场景客观题。

客观题可以评估协议推理、结果预测、配置解读和排障路径，但不能单独证明候选人能够独立完成真实配置、变更沟通或生产操作。后续可通过实验或模拟面试补充，不应把客观题得分直接等同于完整岗位胜任力。

### 2.4 能力层级

每道题必须有一个主要能力层级：

| 层级 | 名称 | 典型行为 |
|---|---|---|
| L1 | 识记与理解 | 解释术语、识别协议、比较基本机制 |
| L2 | 应用与计算 | 子网计算、预测选路、选择正确配置或设计 |
| L3 | 故障定位 | 根据拓扑、路由表、CLI、日志或抓包定位根因 |
| L4 | 综合设计 | 在冗余、策略、扩展性、安全和约束之间做权衡 |

首批新题建议比例为 L1 20%、L2 40%、L3 30%、L4 10%。该比例是初始设计值，后续根据答题数据调整。

## 4. 主要不足与风险

### 4.1 通用网络基础没有形成体系

当前缺少系统覆盖：

- OSI／TCP-IP 分层和封装；
- TCP／UDP、端口和基本传输行为；
- Ethernet、MAC 学习、帧转发和泛洪；
- ARP、NDP、ICMP／ICMPv6；
- VLAN、802.1Q、三层交换和 VLAN 间路由；
- STP／RSTP、LACP、LLDP；
- 物理接口、速率、双工、误码和光链路问题。

风险：候选人可能熟悉某个 DN42 配置技巧，却无法解释基本的端到端转发过程。

### 4.2 IP 题有场景但缺少基础递进

现有题目涉及 DHCP、静态 IPv6、mtr、MTU 和汇总，但未系统覆盖：

- VLSM、前缀边界、重叠前缀和汇总；
- 路由表字段、RIB／FIB、递归下一跳；
- 最长前缀匹配、管理距离／preference 和 metric；
- connected、default、host、floating static route；
- ECMP、非对称路由、黑洞和环路；
- SLAAC、RA、DHCPv6、NAT44／CGNAT、NAT64／DNS64、DS-Lite。

### 4.3 动态路由严重不足

OSPF 只有少量设计和 WireGuard 场景题，IS-IS 为零。缺少：

- OSPF 邻居状态机、网络类型、DR／BDR、LSA、区域和路由选择；
- OSPFv3；
- IS-IS 的 NET／NSAP、L1／L2、LSP、DIS、metric、overload 和多拓扑；
- 重分发、过滤、汇总、默认路由、路由回馈；
- BFD、快速收敛和高可用。

这与运营商网络工程师岗位目标不匹配。

### 4.4 BGP 数量与能力覆盖不成比例

已有 BGP 题偏向社区、会话、RR 基础、ROA 和 DN42 故障场景，仍需补齐：

- FSM、BGP 报文、定时器、update-source 和 multihop；
- 下一跳处理和下一跳不可达；
- LOCAL_PREF、AS_PATH、ORIGIN、MED 等属性及选路；
- prefix-list／prefix-set、AS_PATH 正则、策略顺序和默认动作；
- 多归属下的出入站流量工程；
- RR 高级规则、confederation、max-prefix、GTSM、认证；
- BFD、Graceful Restart、Add-Path、BGP PIC。

涉及选路顺序时必须明确平台，不能把 Cisco、BIRD、FRRouting 等不同实现的所有细节抽象成同一个所谓“通用顺序”。

### 4.5 运营商核心技术基本空白

当前没有形成 MPLS、L3VPN／L2VPN、SR-MPLS、SRv6、QoS、组播、运营商高可用和网络保障等内容。若题库目标包含向 CCNP Service Provider 看齐，这些领域必须进入第二阶段路线图。

### 4.6 筛选结构不足

1. 题目级标签结构已经可用，但目前只有第 1 题有示范标签，其余 31 题尚未覆盖，仍无法对全库可靠输出 IP、IGP、BGP 等领域小分。
2. 只有一个固定集合，重复练习和筛选的曝光控制有限。
3. 所有题目同分，未体现复杂场景题和基础题之间的测量差异。
4. 当前仅设总通过分，擅长 DNS／DN42 的候选人可能用优势领域抵消核心路由能力不足。
5. 尚无量表校准依据，不宜在缺少答题数据时直接提高通过分或宣称题目具有稳定的区分度。

### 4.7 培养反馈不足

平台已支持结构化逐项解析、题目级整体解析和参考链接，并能在练习点击“检查”后展示；但目前只有第 1 题完成示范内容，其余 31 题仍只有答案而缺少学习反馈。后续补齐时必须逐题技术复核，不能把生成解析当作无需审查的批量文本工作。

| 编号 | 题号 | 问题 | 处理结果 | 状态 |

## 8. 题目设计与审查规范

### 8.1 每题必填设计信息

在正式写入 XML 前，每道题应在编写清单或评审记录中明确：

- 稳定题号；
- 领域和子考点；
- 能力层级 L1—L4；
- 题型和分值；
- 题干所依赖的平台、版本和前提；
- 正确答案及逐项理由；
- 权威参考或实验验证依据；
- exhibit 资源及替代表述；
- 技术复核状态。

在平台支持前，这些信息至少需要记录在本文档关联的编写清单中；不能长期只存在于对话或提交说明里。

### 8.2 题干规范

1. 一题只设一个主要考查目标，允许多个知识协同，但不得把多个无关问题拼成一题。
2. 明确“Choose one／two／three”，并确保正确项数量一致。
3. 避免不必要的双重否定、模糊数量词和依赖常识猜测的表述。
4. 明确直连／多跳、地址族、路由方向、策略应用点、默认动作和既有配置。
5. 厂商相关行为必须写明平台；标准行为与实现特有行为必须区分。
6. 不使用未经定义的内部术语作为唯一解题钥匙；DN42 特有术语应提供场景或参考资料。
7. 所有正确结论必须能由题干和 exhibit 推出，不能依赖题干外的隐含拓扑。

### 8.3 选项与答案规范

- 干扰项应代表真实误概念或常见误操作，不得只是明显荒诞的凑数项。
- 选项长度、粒度和术语风格尽量一致，避免通过措辞泄露答案。
- 多选题不得存在“部分正确但题干未说明是否选择”的灰区。
- 修改答案时重新检查所有选项，不能只替换正确项编号。
- 对有争议的技术行为进行第二人复核或最小实验验证。
- 练习模式应逐步增加答案解析，解释正确项和关键干扰项，而不只是重复答案。

### 8.4 场景与拖拽题规范

- 拓扑图必须有清晰接口、地址、AS、区域和方向信息。
- CLI 或日志只保留解题所需内容，避免无关信息造成非技术性阅读负担。
- 拖拽适合协议状态顺序、排障步骤、概念匹配、标签操作和策略执行顺序。
- 拖拽题必须说明是否使用全部候选项、是否允许重复使用，以及连接数量。
- 图片不能成为唯一信息载体；必要时在题干中提供关键文本，保证可访问性和可维护性。

### 8.5 验收清单

每批题目完成前必须确认：

- [ ] 题号唯一且历史题号未被无意复用；
- [ ] 选择数量、正确答案数量和评分逻辑一致；
- [ ] exhibit 路径有效，资源已纳入仓库；
- [ ] XML 符合当时 schema，并能被项目加载；
- [ ] 新题的技术答案经过复核；
- [ ] 运行 `git diff --check`；
- [ ] 运行与变更范围相适应的 Go／E2E 测试；如涉及加载、评分或前端展示，必须覆盖对应回归；
- [ ] 本文档的基线、任务状态和变更台账已回写。

## 9. 元数据、报告与分池设计

### 9.1 已实现的题目元数据结构

2026-11-21 完成 `DCNA-META-001`：Schema、Go 加载模型、练习 assessment 和前端均已支持下列信息。业务能力已经可用，不等于 DCNA 全库内容已经补齐。

| 字段 | XML 表达 | 示例 | 用途 |
|---|---|---|---|
| `domain` | `<label key="domain" value="IGP" />` | `IGP` | 领域统计和抽样 |
| `subdomain` | `<label key="subdomain" value="OSPFv3-neighbor" />` | `OSPFv3-neighbor` | 精细覆盖分析 |
| `level` | `<label key="level" value="L3" />` | `L3` | 能力层级和难度结构 |
| `skill` | `<label key="skill" value="troubleshoot" />` | `troubleshoot` | 区分识记、应用、排障、设计 |
| `platform` | `<label key="platform" value="BIRD 2.x" />` | `BIRD 2.x` | 避免实现差异造成歧义 |
| `version` | `<label key="version" value="1" />` | `1` | 题目修订追踪 |
| `status` | `<label key="status" value="active" />` | `draft/review/active/retired` | 题目生命周期 |
| 整体解析 | `<explanation>...</explanation>` | 总结解题依据 | 培养反馈 |
| 逐项解析 | `<option>文本<explanation>...</explanation></option>` | 分别说明正确项和干扰项 | 培养反馈 |
| 参考链接 | `<references><reference href="...">标题</reference>...</references>` | RFC、官方文档、实验记录 | 技术审查和学习反馈 |

一个题目可放置任意多个 `label`，同一个 key 也可用不同 value 重复出现，以承载多值业务标签。标签是弱类型元数据，领域编码、能力层级和生命周期值仍须遵守本文档约定，不能由作者随意创造同义值。

### 9.2 实施约束与展示边界

1. 新增字段全部可选，旧题库无需为元数据改造重写；已有题号、题型、分值和答案保持不变。
2. 题目标签位于 `description` 之后；整体解析和参考链接位于 `correctanswer` 之后；选项解析直接跟随对应选项文本。
3. 业务标签可在题目下发时保留；正确答案、逐项解析、整体解析和参考链接属于答案敏感信息，必须在未检查的题目及会话当前题中剥离。
4. 练习模式只有点击“检查”取得 assessment 后才展示学习反馈；逐项解析按选项 ID 关联，不能依赖显示顺序。认证考试 assessment 继续省略原题及其反馈。
5. HTTP(S) 参考链接在新窗口打开；其他 URI 仅显示为文本，避免不可信题库注入可点击的非 Web 协议链接。
6. 报告至少提供 NF／IP／IGP／BGP 小分；完成阶段 2 后增加 SP，后续再增加 OPS 和 DN42。该报告能力尚未实现，不因标签结构可用而标记完成。
7. 总通过分与领域门槛是不同机制，不能互相替代。
8. 本轮仅第 1 题有完整示范，其余 31 题由 `DCNA-META-002` 后续逐题复核补齐。

### 9.3 练习与筛选分池

- **练习池**：允许反复作答，提供解析、参考和相似题推荐。
- **筛选池**：控制答案展示，按领域和能力层级抽样，记录题目曝光。
- **待复核池**：新题先用于低风险练习或试测，完成技术和数据复核后再进入筛选池。

## 10. 每轮改进的标准实施步骤

1. **读取**：阅读本文档、当前 XML、相关图片和近期提交；确认是否存在未解决的 QA 或设计决策。
2. **登记**：确定任务编号、目标题数、领域、能力层级和验收标准；临时新增工作也要先登记。
3. **编写清单**：先写逐题考点和场景，不直接以随机题干堆积数量。
4. **技术验证**：核对 RFC、官方文档或最小实验；平台相关行为注明版本。
5. **实施**：修改 XML 和资源文件，保持既有题目及无关内容不变。
6. **复核**：检查题干、选项、答案、选择数量、图片、英文和评分。
7. **测试**：执行 XML 加载／schema 验证和适用的项目测试；展示或评分变化需增加对应回归。
8. **回写**：更新第 3 节基线、第 6／7 节任务进度、第 11 节指标和第 12 节变更台账。
9. **复盘**：记录未达到计划的原因、争议题、后续修复和是否调整路线图。
